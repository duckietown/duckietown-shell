
# Information for Duckietown Shell developers

### Docker

To launch the Duckietown Shell in Docker, run the following command:

    $ docker run -it duckietown/duckietown-shell
    
Note: the Duckietown Shell is supposed to be run natively from the host.

### Local commands development

Use the [source-development workflow](#source-development) before setting an
override for your local copy of the commands:

    export DTSHELL_COMMANDS=/path/to/my/duckietown-shell-commands

### Source development

Official wheels contain compiled launch, dispatch, authorization, device,
profile, and environment modules. They reject `DTSHELL_LIB`, `DTSHELL_COMMANDS`,
and `DTSHELL_PYTHONPATH`, including empty values. There is no release flag that
disables integrity verification.

Run the Python checkout explicitly for development instead of installing it
editable or invoking the official wheel's `dts` entry point. From this repository
on Linux or macOS:

```shell
python3.12 -m venv .venv
.venv/bin/python -m pip install -r lib/dt_shell/assets/requirements.txt \
    "Cython>=3.0.12,<4" "docker>=6.1.3,<7"
PYTHONPATH="$PWD/lib" DTSHELL_COMMANDS=/path/to/duckietown-shell-commands \
    .venv/bin/python -m dt_shell_cli.dts version
```

On Windows, use `.venv\Scripts\python.exe` and set `$env:PYTHONPATH` to the
absolute `lib` directory in PowerShell. Source code still performs the normal
plan checks; it is a development route, not an authenticated official release.
`Cython` supplies the source-mode `cython.compiled` marker without compiling the
checkout.

### Signed native releases

Release wheels target CPython 3.10, 3.11, and 3.12 on:

| System | Architectures |
| --- | --- |
| Linux (manylinux/glibc) | x86-64, ARM64 |
| macOS | Intel, Apple Silicon |
| Windows | x86-64 |

All 15 combinations must be present before publication. Alpine/musl, Windows
ARM64/32-bit, alternative Python implementations, and other Python minors are not
official-wheel targets.

The protected modules have no `.py`, `.pyc`, `.pyx`, or generated C fallback in
the wheel. The native bootstrap embeds the release verification public key,
verifies the signed manifest before loading DTS, and checks again at delegation
and command dispatch. The manifest covers the final native binaries, remaining
package sources, embedded commands, assets, and immutable wheel metadata.
Normal installer metadata and generated bytecode caches are not signed.

Use a **dedicated Ed25519 release-signing key**, not Hub token keys. Once, outside
the repository, generate the key pair using Python 3.12 in an isolated build
environment:

```shell
python3.12 -m venv /path/to/release-venv
make release-deps PYTHON=/path/to/release-venv/bin/python
/path/to/release-venv/bin/python tools/release.py keygen \
    --private-key /secure/location/dts-release-private.pem \
    --public-key /secure/location/dts-release-public.hex
```

The destination directories must already exist. The key generator rejects
existing files and paths inside this repository; on POSIX it creates the private
file with mode `0600`. On Windows, restrict its ACL to the signing operator.
Store the private PEM in a secret manager and never commit it, add it to build
artifacts, or pass it to CircleCI's environment-dumping jobs.

Configure GitHub Actions:

| Setting | Kind | Value |
| --- | --- | --- |
| `DTS_RELEASE_PUBLIC_KEY` | Repository variable | 64 lowercase hexadecimal characters from the public-key file |
| `DTS_RELEASE_SIGNING_KEY` | Repository secret | Complete unencrypted Ed25519 private PEM, preserving newlines |
| `PYPI_USERNAME` | Existing repository secret | PyPI token username, normally `__token__` |
| `PYPI_TOKEN` | Existing repository secret | PyPI upload token |

The public key is required at **build time**; no runtime signing secret or
public-key override is supported. A missing/invalid key or compiler is a build
error, not a reason to produce a pure-Python wheel. Key rotation requires
rebuilding the wheels with the new embedded public key and signing them with the
matching private key.

The **Upload Python Package** workflow builds and repairs platform wheels with
cibuildwheel, then signs their final bytes in a separate job. Only that job
receives the release private key. It installs and tests each signed wheel on its
matching OS/architecture/Python before allowing publication. The **Automated
Release** workflow explicitly dispatches it after creating the GitHub release:
releases made with `GITHUB_TOKEN` do not otherwise trigger a second workflow.
You can also publish a GitHub release manually or dispatch **Upload Python
Package** with an existing tag.

The Makefile no longer publishes source distributions:

```shell
export DTS_RELEASE_PUBLIC_KEY="$(cat /secure/location/dts-release-public.hex)"
make release-wheels PYTHON=/path/to/release-venv/bin/python WHEELHOUSE=wheelhouse
export DTS_RELEASE_SIGNING_KEY_FILE=/secure/location/dts-release-private.pem
make release-seal PYTHON=/path/to/release-venv/bin/python WHEELHOUSE=wheelhouse
```

Local cibuildwheel builds only platforms supported by the build host; use the CI
matrix to produce the complete cross-platform release. Sign **after**
auditwheel/delocate repair; modifying a sealed wheel invalidates its signature.
Linux cibuildwheel builds require Docker or Podman, macOS requires Xcode tools,
and Windows requires MSVC. Run cibuildwheel itself with Python 3.11 or 3.12,
even when building Python 3.10 wheels.

Download the complete `signed-wheels` CI artifact into a new `dist` directory
when using manual upload. Then:

```shell
make release-verify PYTHON=/path/to/release-venv/bin/python DIST=dist
make upload PYTHON=/path/to/release-venv/bin/python DIST=dist
```

`make upload` verifies signatures, native entry points, Python metadata, wheel
RECORDs, the release version, and all 15 targets before invoking Twine. It rejects
unsigned/universal wheels, source archives, duplicate targets, and stale files.
Keep `TWINE_USERNAME`/`TWINE_PASSWORD` in the usual secure publishing environment.
`make bump-upload` deliberately stops with migration guidance: one workstation
cannot build and publish all supported operating systems. `make bump` still
bumps and pushes as before; it does not create a GitHub release or publish wheels.

Native profile environments must match the installed DTS interpreter's Python
minor version, OS, and architecture. An incompatible existing or custom
`DTSHELL_VENV_DIR` produces an actionable error instead of attempting to load a
different ABI. Reset/recreate an old profile environment with the installed
interpreter after changing Python versions.

This is tamper resistance for ordinary installations, not an independent local
trust anchor. Public source, older clients, external command repositories,
third-party dependencies, generated bytecode caches, entry-point scripts, and
in-memory Python monkeypatching are not authenticated by the wheel manifest.
Commands remain updateable; signing their provenance is a separate task.
Protected-server/private-registry checks are still needed against determined
users. `daffy` remains plan-free in an intact official installation.
 
### Use local challenge server

Use the env variable `DTSERVER` to work on a local server:

    export DTSERVER=http://localhost:6544/
 

### Plan authorization for `ente`

The `ente` distribution, including its staging variant, requires the free
"Independent User" plan or an active "Institutional User" plan. The "Instructor"
plan is an add-on to the "Institutional User" plan and does not grant `ente`
access by itself. Staff and superusers are exempt from both the plan requirement
and the computer limit.
The `daffy` distribution and its staging variant do not require a plan. Core token, profile, and command
management commands remain available, and ordinary token generation is unchanged.

DTS obtains a signed, non-renewable authorization for `ente` from
`/api/v1/auth/token/ente/` and caches it per profile, identity token, and Hub.
The grant is bound to the user, Hub, and registered computer. Its signed expiration
is the earlier of 24 hours and any recorded expiration of the plan granting access.
Redeemed seats for the "Institutional User" plan use their parent plan's expiration;
the "Instructor" plan does not extend it. Qualifying plan flags without a recorded
validity period, including enrollment in the free "Independent User" plan, retain daily authorization
with no recorded plan expiration.
The cached grant is checked locally and refreshed on demand after at most 24 hours,
or earlier if its signed expiration is reached. Without a valid cached grant,
an unavailable Hub blocks `ente` commands but does not block `daffy` commands.

Each non-staff account can register one DTS computer. Identity-token or cache
copies do not authorize a different computer in the supported client. The
fingerprint hashes the Linux machine ID, macOS platform UUID, or Windows
MachineGuid; VMs, separate OS installations, and reinstalls may have different
identities. No raw machine ID is sent to Hub.

```shell
dts subscription status
dts subscription transfer
```

Status distinguishes **Account plans** (all plans listed on the account, including
add-ons) from **Plan granting 'ente' access** (the qualifying "Independent User"
plan or "Institutional User" plan). The **Plan requirement for 'ente'** shows
whether the account meets that requirement or is exempt; it is not a promise that
the current computer can obtain a grant during a pending transfer.
It also shows any recorded plan expiration, the registered computer, the latest
expiry among its issued authorizations, and any pending transfer. User-facing
dates use a readable UTC format, such as `10 October 2026 at 14:38 UTC`;
seconds are included when relevant. Machine-readable API dates remain ISO 8601.
DTS warns about a recorded plan expiration within three days only when fetching a fresh grant.
Run transfer on the replacement computer. Running it on the already-registered
computer with no pending transfer is a no-op: the confirmation says the computer
is already registered and no transfer is needed, without a redundant timestamp.
An initial registration or an immediate transfer is reported as registered now;
run an `ente` command to request authorization. A scheduled transfer shows its
readable availability date and explains that new authorizations are paused.
The transfer response's availability time is the earliest time an authorization
can be requested, not a new grant's expiration. Transfer requests do not issue
authorizations or change existing token expiry dates.
Hub stops issuing grants during the pending transfer and activates the replacement
only after every old grant expires (at most 24 hours). Switching credentials or profiles does not reset this
per-user registration. These management commands remain available without authorization for `ente`,
but require an ordinary DT2 identity token.

To use local code with a development HTTPS Hub:

```shell
DTSHELL_LIB=/path/to/duckietown-shell/lib \
DTSHELL_COMMANDS=/path/to/duckietown-shell-commands \
DTHUB_HOST=localhost:8443 \
PYTHONPATH=/path/to/duckietown-shell/lib \
/path/to/source-venv/bin/python -m dt_shell_cli.dts devel info
```

`DTHUB_HOST` is a hostname with an optional port; `DTHUB_URL` overrides the full
URL used by the shell. A development Hub using different signing keys requires
an isolated client configured to trust its development public keys. Self-signed
HTTPS certificates must also be trusted; do not disable certificate verification.

This is an official-client policy, not tamper-proof anti-sharing. Machine IDs
can be spoofed or cloned, and public clients can be modified to bypass local
checks. It also does not stop already-running/downloaded robot images. Enforcing
access against hostile clients requires a protected server or image registry.

### Advanced configuration

By default, Duckietown Shell uses the folder `~/dt-data` for storing log data and other cache data.

Alternatively, you can use the `--dt-data` argument to choose a different folder:

    $ dts logs --dt-data ![dir] ![command]

Alternatively, the directory can be specified using the environment variable `DT_DATA`.

    $ DT_DATA=/tmp/data dt logs summary

    $ dts logs download 20171124170042_yaf

    $ dts logs copy -o ![output dir] 20171124170042_yaf
